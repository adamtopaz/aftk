# `aftk_setup` Lake script

`aftk_setup` is a Lake script defined in `lakefile.lean`.
Its job is to make the current Lake workspace look like an AFTK-aware pi project without requiring manual `.pi/` setup.

The script logic lives in `lakefile.lean`, while the appended system-prompt source lives in `src/hosts/pi/APPEND_SYSTEM.template.md`.

Run it with:

```text
lake run aftk_setup
```

Show help with:

```text
lake run aftk_setup --help
```

## What the script writes

The script creates or refreshes two project-local files under the **current Lake workspace root**:

```text
.pi/extensions/aftk-toolkit.ts
.pi/APPEND_SYSTEM.md
```

### 1. `.pi/extensions/aftk-toolkit.ts`

This is a generated local pi extension shim.
It re-exports AFTK's default pi extension entrypoint from the resolved `aftk` package location.

In this repository itself, the generated file currently looks like:

```ts
// Generated by `lake run aftk_setup`. Re-run to refresh.
export { default } from "../../src/hosts/pi/extension.ts";
```

In a dependent workspace, the import specifier may instead point into a path dependency or into `.lake/packages/aftk/...`, depending on how Lake resolved the dependency.

### 2. `.pi/APPEND_SYSTEM.md`

This is a generated appended system prompt for pi.
It adds AFTK-specific guidance without replacing pi's default system prompt.

The generated file is built from:

```text
src/hosts/pi/APPEND_SYSTEM.template.md
```

with the standard generated-file marker prepended at write time.

The prompt template currently emphasizes:

- reading `entrypoint.md` first when present
- selective, inspect-first project exploration
- making one meaningful chunk of progress per turn rather than trying to finish everything at once
- treating informal nodes, knowledge-base nodes, Lean source, and related metadata as orchestration artifacts for stigmergic coordination
- important safety rules about transient tactic state and persisted proof edits

## Discovery model

The script does its discovery through Lake rather than by guessing filesystem layout.

At a high level it does this:

1. read the current workspace with `getWorkspace`
2. treat `ws.dir` as the project being configured
3. find the `aftk` package in that workspace
4. resolve the package's `src/hosts/pi/extension.ts` entrypoint
5. resolve the package's `src/hosts/pi/APPEND_SYSTEM.template.md` prompt template
6. generate the `.pi/` files under the current workspace root

This matters because the script is meant to work in two situations:

- inside `aftk` itself
- inside another Lake workspace that depends on `aftk`

So the configured project root is the **current workspace**, not necessarily the `aftk` package directory.

## Import-specifier policy

The generated shim prefers a relative import specifier from:

```text
.pi/extensions/aftk-toolkit.ts
```

to the resolved AFTK pi extension entrypoint.

If a relative import is not practical, the script falls back to an absolute import specifier.
On Windows, absolute filesystem imports are emitted as `file:///...` URLs.

The import-specifier helpers live directly in `lakefile.lean`.
They normalize path separators for TypeScript module loading.

## Idempotence and overwrite safety

The script is intentionally safe to rerun.
For each generated file it uses one of three plans:

- `create`
- `overwrite`
- `unchanged`

The overwrite rule is conservative:

- if the destination does not exist, it is created
- if it already has the exact desired content, nothing changes
- if it begins with the generated-file marker, it may be updated
- otherwise the script refuses to overwrite it

So user-managed `.pi/extensions/aftk-toolkit.ts` or `.pi/APPEND_SYSTEM.md` files are protected unless they were originally generated by this script.

## Generated-file markers

The two generated files use different marker styles because one is TypeScript and one is Markdown:

- shim marker: `// Generated by \`lake run aftk_setup\`. Re-run to refresh.`
- prompt marker: `<!-- Generated by \`lake run aftk_setup\`. Re-run to refresh. -->`

These markers are how the script decides whether a file is still script-managed.

## Command-line behavior

Accepted invocations are:

```text
lake run aftk_setup
lake run aftk_setup --help
lake run aftk_setup -h
```

Unexpected arguments are rejected with a short usage message.

Current exit-code behavior:

- `0` on success
- `0` on `--help`
- `1` on operational failure
- `2` on invalid usage

## Success summary

On success, the script prints a short summary that includes:

- the workspace root
- the discovered `aftk` package path
- the resolved pi extension entrypoint
- the resolved prompt-template path
- whether the shim was installed, updated, or already up to date
- whether the appended prompt was installed, updated, or already up to date
- the final import specifier
- a reminder to use `/reload` if pi is already running

## Typical workflows

### Inside this repository

Run:

```text
lake run aftk_setup
```

Result:

- `.pi/extensions/aftk-toolkit.ts` points at `src/hosts/pi/extension.ts`
- `.pi/APPEND_SYSTEM.md` contains the generated AFTK agent guidance

### Inside a dependent Lake workspace

Assuming the workspace depends on the Lean package `aftk`, run the same command:

```text
lake run aftk_setup
```

Result:

- the `.pi/` files are written in the dependent workspace
- the shim points at the resolved `aftk` package location discovered by Lake
- pi can load the toolkit as a project-local extension from that dependent workspace

## What the script does not do

The current script intentionally does **not**:

- edit `.pi/settings.json`
- start pi for you
- issue `/reload` automatically
- install npm packages
- AFTK toolkit runtime executable specs
- perform broader environment bootstrap beyond the two generated `.pi/` files

Its scope is deliberately narrow: make the current Lake workspace discover the AFTK pi extension and appended prompt safely.
